# Human-required items

Format: `- [task NN] <what> — why an agent can't — what is prepared — exact next step`

- [task 01] Create the dev and prod Firebase projects and choose owners/billing plan — needs console access, account ownership and billing decisions an agent does not have — config validation, `.env.example` and tests are ready, no project ids are invented — In the Firebase console create one dev and one prod project, assign owners, pick the plan, and record each project id.
- [task 01] Set EU data location (decide on the Identity Platform upgrade) — a console-only, irreversible, billing-affecting choice — nothing in code depends on it — Choose the EU location for each project and decide whether to upgrade to Identity Platform; note the decision in the task file.
- [task 01] Enable Email/Password sign-in, disable Anonymous, turn off email enumeration protection — console-only settings — the backend expects password accounts only — In Authentication > Sign-in method enable Email/Password and disable Anonymous; in Authentication settings turn email enumeration protection off, for both projects.
- [task 01] Configure authorized domains / web origin for the app — requires the real deployed domains and console access — `APP_BASE_URL` is handled in a later task — In Authentication > Settings > Authorized domains add the dev and prod web origins.
- [task 01] Provide `FIREBASE_PROJECT_ID` per environment and, only if running outside Cloud Run/GKE, service-account JSON as `FIREBASE_CREDENTIALS_JSON` via the secret manager — agents must not see or invent credentials — validation requires the project id (no default), treats credentials as an optional JSON object, and never echoes values — Set `FIREBASE_PROJECT_ID` in each environment's config and store the service-account JSON (if needed) in the secret manager, never in git.
- [task 01] Hand the public Firebase web config (apiKey, authDomain, projectId, appId) to the app team — it comes from the console — nothing backend-side to prepare — Copy the web app config from Project settings for dev and prod and send it to the frontend repo owners.
- [task 01] Verify AC-4: disabling a user makes token refresh fail within 60 minutes — needs a real Firebase project and a real user — the emulator host setting allows local runs but does not exercise this behavior — In the dev project create a test user, sign in, disable the user in the console, then confirm refresh fails within 60 minutes.
- [task 06] Enforce HTTPS-only serving (FR-11) and set the proxy hop count — TLS termination, HTTP-to-HTTPS redirect/HSTS are delegated to the deployment platform (load balancer / Cloud Run), not application code; the number of proxies in front of the app is only known at deploy time — the app trusts exactly `TRUST_PROXY_HOPS` proxy hops (default 0, never `true`; see `.env.example`), which decides the client IP used by the failed-auth rate limit; API docs (Swagger) are not served when NODE_ENV=production — Terminate TLS and redirect/deny plain HTTP at the platform; set `TRUST_PROXY_HOPS` per environment (Cloud Run / one load balancer: 1; direct exposure: 0).
- [task 06] Known deviation from FR-1: signing keys are refetched by firebase-admin on cache max-age expiry, not on every unknown `kid` — the SDK does not expose this — nothing to prepare — Accept, or request a custom verifier with kid-miss refetch if key-rotation lag is a concern.
- [task 06] Verify token verification against real Google signing keys (NFR-4, FR-1) and key-fetch outage behaviour (503) — needs a real Firebase project (task 01 console work) and network access to Google's certificates — the e2e suite runs against a real Firebase Auth emulator in Testcontainers (`test/e2e/support/firebase-emulator`), but the emulator issues unsigned tokens, so RS256 signature checking, key caching and real bad-signature rejection are only covered by firebase-admin itself, not by our tests — Against the dev project sign in with a real user, call an authenticated endpoint with the ID token, then with a token whose signature is altered (expect 401 `unauthenticated`).
- [task 06] Decide on a shared rate-limit store before running more than one instance — the in-memory limiter is per instance, so the effective limit is up to N times 60/min with N instances — `RateLimiter` is isolated behind one class with an injectable clock — If the service will scale horizontally, choose a shared store (for example Redis) and ask for the limiter to be swapped.
- [task 06] Provide the real Terms of Service and Privacy Policy version identifiers recognised by `PUT /me` consent — the legal documents and their version naming are owned by the product/legal owner and must not be invented — `CONSENT_TERMS_VERSIONS` and `CONSENT_PRIVACY_VERSIONS` (comma-separated, required, no defaults) are validated at boot, `.env.example` and tests use placeholders (`TERMS-PLACEHOLDER-1`, `PRIVACY-PLACEHOLDER-1`) — Obtain the published version identifiers, put them in each environment's config, and have the app team ship the same identifiers in the client build configuration.
- [task 06] Confirm two choices the spec leaves open: a verified token without an email returns 403 `incomplete-identity` (a legacy type outside the spec's registry), and a whitespace-only `name` returns `REQUIRED` rather than `TOO_SHORT` — product/API-owner decisions an agent should not make silently — both are implemented and covered by tests — Confirm or tell the implementer to change the status/type or reason code (and, if kept, add `incomplete-identity` to the spec 06 registry).
